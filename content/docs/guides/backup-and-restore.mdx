---
title: Backup and restore
description: Export your recordings, transcripts, and audio so you can leave at any time.
---

Riffado has two separate export paths, deliberately. They serve
different jobs:

- **`/api/backup`** — a complete JSON archive of every recording row
  and transcript that belongs to you. Built for full disaster
  recovery and migration off the instance.
- **`/api/export`** — every recording's transcript flattened into one
  human-readable file (`txt`, `srt`, `vtt`) or a `json` dump. Built
  for handing transcripts to other tools, not for backup.

The audio files themselves live in your configured storage backend
(local volume or S3 bucket) and are backed up the same way you'd back
up any other binary blob.

## Backup: the full archive

**Settings → Export/Backup → Create Backup** (or `POST /api/backup`)
queues a job that builds a **zip containing everything**: the audio for
every recording, its transcripts and summary, and a `manifest.json`
describing what went in. It is built in the background — the request
returns immediately rather than blocking while audio streams out of
storage — and the panel reports progress.

A recording whose audio cannot be read does not fail the archive; it is
noted in the manifest and skipped, so you still get everything else.

Finished archives stay downloadable for **7 days**, then a cleanup pass
deletes them.

The contents are **plaintext**. Riffado's at-rest encryption decrypts
every field before writing it into the archive, because the backup is
*your* export of your own data — you own it from this point. Treat the
file the way you would an unencrypted database dump: store it
encrypted, restrict access, don't email it.

### Where archives are written

By default an archive is written to the same storage as the recordings,
which on a local install means the zip lands in the same folder as the
audio it contains. Set
[`BACKUP_STORAGE_PATH`](../self-hosting/environment-variables) to a path
on separate storage and archives go there instead — worth doing before
turning on a schedule, since otherwise each archive roughly doubles that
folder and shares a disk with the original.

### On a schedule

**Backup frequency** (daily, weekly or monthly) builds one
automatically. The scheduler queues a job when a user has chosen a
cadence, has nothing already queued or building, and has had no job at
all created within that window — so a cadence produces at most one
archive per window, and a job that fails for a durable reason is not
retried on every pass.

Combined with the 7-day retention above, a *monthly* cadence means the
archive is gone for three weeks of every month. If a backup should
always be available, use daily or weekly, or copy each archive somewhere
else when it lands.

> **Backup is not export.** Two different things with confusingly
> similar names. A *backup* is this asynchronous zip, audio included.
> An *export* (below) is a synchronous text download of transcripts and
> summaries, with no audio. Export is for the words; backup is for
> everything.

## Backup the audio files

- **Local storage backend.** The Docker volume that mounts at
  `/app/audio` inside the container holds every audio file. Snapshot
  it the same way you snapshot any other volume — `restic`, `rsync`,
  ZFS snapshots, your choice.
- **S3 backend.** Whichever bucket you configured already lives
  outside the instance. Enable versioning, cross-region replication,
  or a lifecycle copy job on the bucket itself.

The path layout inside the bucket / directory is
`{userId}/{filename}.mp3`, with `(2)`, `(3)`,&nbsp;… suffixes appended
on collisions.

## Bulk transcript export

`GET /api/export?format=<fmt>` flattens every one of your recordings
into a single file:

| Format | Content                                                  |
| ------ | -------------------------------------------------------- |
| `json` | One JSON document with every recording + transcript      |
| `txt`  | Plaintext, one block per recording (filename, time, text)|
| `srt`  | SubRip subtitles, all recordings concatenated            |
| `vtt`  | WebVTT subtitles, all recordings concatenated            |

The default format is whatever you set as **Settings → Export/Backup
→ Default export format**, falling back to `json`. The **Export All**
button in that same panel calls this endpoint.

## Markdown documents alongside the audio

Transcripts and summaries live in Postgres, encrypted at rest, so a file
manager sees only audio. **Settings → Export/Backup → Documents
alongside audio** changes that: with **Export transcripts** or **Export
summaries** on, every completed run also writes a markdown file into
storage, named after the recording's audio file.

```
{userId}/Board meeting.mp3
{userId}/Board meeting.transcript.md
{userId}/Board meeting.summary.md
```

Each file carries YAML front matter (title, recorded timestamp,
duration, language, provider, model) followed by the text. Summaries
render the summary, key points and action items as sections, skipping
whichever the provider left empty.

The toggles apply to transcriptions and summaries produced from that
point on. **Export all existing** in the same panel runs the backfill
over recordings you already have; it writes inline, so a large library
keeps the request open for a while.

This works on any storage backend. With the local backend it means the
markdown lands in the same directory as the audio, which is directly
useful when that directory is a bind mount on the host. On S3 the files
become objects next to the audio keys.

Export failures never cost you data: a storage error is logged and the
transcript or summary is still saved.

## Retention: deleting old data on purpose

**Settings → Storage → Auto-delete old data** removes data from
recordings that have passed a retention period you set (1-365 days,
counted from when the recording was made).

Three kinds can be selected independently:

| Kind | What goes | Recoverable? |
|---|---|---|
| Audio | The blob in storage | No. Re-syncing only brings it back if Plaud bumps the recording's version. |
| Transcript | The `transcriptions` rows | Only by re-transcribing, which needs the audio. |
| Summary | The `ai_enhancements` row | Only by regenerating, which needs the transcript. |

Audio is almost all of the disk footprint, so "delete audio, keep the
text" reclaims nearly everything while leaving the library searchable.
The other combinations are available because they are sometimes what you
want — keeping only summaries, for instance.

Some specifics worth knowing before you switch it on:

- **The recording itself is never deleted.** Its title, date and duration
  stay in the list, marked with what was removed. A recording whose audio
  is gone shows a note instead of a player, and its audio endpoints return
  `410 Gone` rather than an error.
- **Nothing is selected by default**, including audio. The sweep does
  nothing until you pick at least one kind, so upgrading an instance that
  had the old (inert) auto-delete toggle switched on cannot start deleting
  behind your back.
- **Settings shows how many recordings the policy applies to** before you
  save it.
- **Markdown sidecars are left alone.** `<recording>.transcript.md` in your
  storage folder is an export you asked for, not Riffado's copy; retention
  removes the database rows and the audio blob and does not touch files it
  did not put there on your behalf. Delete those yourself if you want them
  gone.
- The sweep runs hourly, in batches, and logs what it removed per user.

## Restore

There is no `POST /api/backup/restore` endpoint today. The backup file
is the export half of the contract — it lets you leave the instance
with your data intact, which is what "export parity" guarantees. If
you need to import a backup into a fresh instance, the supported path
is a Postgres-level restore (the snapshot of the database volume), not
a JSON re-import.

If you need a programmatic re-import — for migrating between
self-host instances, for instance — file an issue with the use case.
It's a deliberate gap, not an oversight, and the right shape depends
on the use case.

## What's encrypted vs. what's plaintext

A reminder, because this trips people up:

- **In the database**, sensitive fields are encrypted at rest with
  AES-256-GCM (see [Encryption at rest](../reference/encryption-at-rest)).
- **In a backup file produced by `/api/backup`**, those fields are
  decrypted before serialization. Your responsibility from there.
- **Audio files in storage** are *not* encrypted by Riffado's
  app-layer encryption — use bucket-level SSE if you need that.
